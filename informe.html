Descripción de la actividad

El objetivo de esta práctica es identificar las ventajas y desventajas del uso de una API RESTful mediante la herramienta Postman. Para ello se creó un workspace con el nombre de la asignatura y, dentro de él, una collection llamada reqres-users con una request por cada método HTTP a probar: GET, POST, PUT y DELETE.

Como repositorio de datos se utilizó https://reqres.in/api/users, un servicio público que simula una API REST de usuarios y responde con los códigos de estado esperados para cada operación. En POST y PUT se envió un cuerpo en formato JSON (crudo, con header Content-Type: application/json), replicando la interacción típica entre un frontend y un backend.

Captura de Pantallas Funcionales

1. Método GET — Listar usuarios

Petición: GET https://reqres.in/api/users?page=2
Resultado: 200 OK — 618 ms.

Se solicita la página 2 del listado de usuarios. Al no requerir body ni headers especiales, el servidor responde inmediatamente con el arreglo data conteniendo los usuarios de esa página.

2. Método POST — Crear usuario

Petición: POST https://reqres.in/api/users
Header: Content-Type: application/json
Resultado: 201 Created — 426 ms.

Se envía el siguiente cuerpo en la pestaña Body → raw → JSON. El servidor genera automáticamente el id y un createdAt, y los devuelve junto con los datos enviados:

{
  "name": "morpheus",
  "job": "leader"
}

3. Método PUT — Actualizar usuario

Petición: PUT https://reqres.in/api/users/2
Header: Content-Type: application/json
Resultado: 200 OK — 420 ms.

Se actualiza el campo job del usuario con id=2. A diferencia de POST, PUT es idempotente: repetir la misma petición deja el recurso en el mismo estado.

{
  "name": "morpheus",
  "job": "zion resident"
}

4. Método DELETE — Eliminar usuario

Petición: DELETE https://reqres.in/api/users/2
Resultado: 204 No Content — 441 ms.

Se elimina el recurso identificado en la URI. El servidor responde sin body, confirmando que la operación se ejecutó correctamente.

Conclusiones

  1. Postman permite comprobar de forma práctica el comportamiento de los métodos HTTP sobre una API RESTful real, sin necesidad de escribir código de frontend: se verificó que GET y PUT devuelven 200 OK, POST devuelve 201 Created junto con el recurso creado, y DELETE devuelve 204 No Content sin body.
  2. La idempotencia de PUT y DELETE, frente al comportamiento no idempotente de POST, es una diferencia técnica clave al diseñar una API: repetir una petición PUT o DELETE sobre el mismo recurso no cambia el resultado final, mientras que repetir un POST crea un nuevo recurso cada vez.
